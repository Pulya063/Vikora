# Захист API та форм

## Реалізовані межі

- Вхідні моделі Pydantic забороняють невідомі поля та неявне перетворення типів. Обмежені довжини, розміри вікна, кількість секцій, відкривання, контактні канали, згода та honeypot. Нульові, службові символи й некоректні Unicode surrogate відхиляються до запису в PostgreSQL. Телефон нормалізується до ASCII `+380XXXXXXXXX`.
- Сумісність профілю та опцій перевіряє PricingService. Ціну обчислює сервер: клієнт не може записати власну суму чи статус заявки. Застаріла версія цін повертає 409.
- SQLAlchemy та advisory lock використовують параметри. Апострофи й SQL-подібний текст у коментарях дозволені як звичайний текст; їх не можна інтерполювати в SQL або відображати через raw HTML.
- Публічний API не приймає файлів: тільки `application/json`, максимум 32 KiB, без стиснення. Обмеження перевіряється також для chunked body. На отримання тіла дається 10 секунд. Це заборона завантаження, а не антивірусний сканер.
- До БД допускається максимум 32 одночасні HTTP-запити на процес. Надлишкові отримують 503. Локальний лічильник обмежує всі запити до 120/хв на адресу, включно з невалідними; пам’ять обмежена 4096 адресами. Вікно фіксоване, можливий сплеск на його межі.
- Додатковий спільний PostgreSQL-ліміт: 8 заявок і 60 розрахунків за хвилину на адресу. Клієнтські `X-Forwarded-For` не використовуються. За Next.js rewrite клієнти можуть мати спільний ліміт за адресою проксі; перед публічним запуском потрібні узгоджені ліміти на довіреному reverse proxy.
- Ідемпотентність заявок з advisory lock і унікальним ключем уже була реалізована. Форма тепер синхронно блокує повторне надсилання та зберігає ключ після мережевої помилки. Зміна payload створює новий ключ. 429/503 враховують Retry-After. Калькулятор скасовує запит після зміни параметрів і не показує застарілий результат.
- Async SQLAlchemy/asyncpg та транзакційна outbox уже існували. Окремий сервіс `worker` доданий у Compose: Telegram/Notion для заявок не затримують HTTP-відповідь. Доставка має повтори; зовнішні сервіси не гарантують exactly-once (зокрема можливий повтор Telegram після збою між доставкою і commit).
- Пул БД обмежений 5+5 з’єднаннями на процес, з тайм-аутами очікування, підключення, SQL і блокувань. Uvicorn у контейнері має обмеження конкурентності, backlog та keep-alive. Ці межі не замінюють захист від DDoS на мережевому рівні.
- Host/Origin перевіряються; CORS має явний список. API-відповіді мають no-store/nosniff; помилки валідації та БД не повертають введені контакти, SQL чи секрети. Frontend має заборону embedding/object та обмеження form-action/base-uri через CSP.

## Передача даних

Шифрування трафіку забезпечує **HTTPS/TLS**, не HTTPX (HTTPX — HTTP-клієнт). Код не може зробити HTTP захищеним: якщо POST уже надіслано відкритим каналом, перенаправлення не приховає його.

Форма блокує надсилання контактів через HTTP поза loopback (`localhost`, `127.0.0.1`, `[::1]`). Локально використовуйте тестові контакти. Сервер у `APP_ENV=production` вимагає HTTPS URL сайту й origins та відхиляє HTTP API-запити (окрім мінімального `/health`). На HTTPS-відповідях API вмикається HSTS.

Перед деплоєм:

1. Налаштувати TLS на reverse proxy для сайту **і API**, редирект HTTP до показу форми, HSTS на зовнішньому сайті, ліміти тіла/часу/частоти на proxy.
2. Задати `APP_ENV=production`, HTTPS `PUBLIC_SITE_URL`, явні `ALLOWED_ORIGINS` та `ALLOWED_HOSTS`. Публічні сторінки документації API у production вимкнені.
3. Compose зараз навмисно запускає Uvicorn з `--no-proxy-headers`. На деплої налаштувати `--proxy-headers --forwarded-allow-ips=<лише IP довіреного проксі>` і направити `/api/v1` з TLS proxy до API. Не використовувати `*`; не приймати forwarded заголовки з Інтернету. До цього production API відмовлятиме у HTTP-доступі.
4. Не виставляти PostgreSQL/API напряму в Інтернет; Compose прив’язує опубліковані порти до loopback. Створити окремого користувача БД з мінімальними правами, замінити локальний пароль, налаштувати резервні копії, секрети, моніторинг і термін зберігання контактів.
5. Узгодити загальний бюджет DB connections і лімітів при додаванні процесів/реплік. Перевірити реальний reverse proxy, PostgreSQL та зовнішні інтеграції навантажувальними тестами.

## Автотести

Із `backend`: `../.venv/Scripts/python.exe -m pytest -q -p no:cacheprovider`.

За замовчуванням тести не використовують робочу БД. Для PostgreSQL-тестів задайте `VIKORA_TEST_DATABASE_URL` з окремою базою, назва якої закінчується на `_test`. Кожен прогін створює випадкову ізольовану схему, seed і прибирає тільки цю схему. Тести використовують ORM metadata; перевірка Alembic міграцій на чистій БД залишається окремим етапом деплою.

Із `frontend`: `npm run test:contract`, `npm run test:forms`, `npm run typecheck`.

Якщо Chromium Playwright не встановлений, можна використати вже встановлений Edge: у PowerShell задайте `$env:FORM_BROWSER_CHANNEL='msedge'` перед `npm run test:forms`. Next dev може автоматично оновити згенерований `next-env.d.ts` та список типів у `tsconfig.json` під свій cache directory.

Контрактний Python-тест запускає справжній TypeScript builder форми через Node та валідує його JSON моделлю QuoteRequest. Браузерні тести запускають окремий Next dev на `127.0.0.1:3105` з окремим cache directory; API-відповіді в цих тестах підмінено для відтворення помилок і затримок. Це перевірка поведінки форми, а не end-to-end доказ запису в БД.
